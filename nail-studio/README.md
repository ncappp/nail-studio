# Pearl · Telegram Mini App

Один мастер, один календарь. Node.js/Vercel, PostgreSQL и Storage в Supabase, Telegram.

## Возможности

- Запись клиента, история страницами по 50 визитов, отмена и перенос с ограничением 12 часов.
- Кабинет мастера, перенос визита, ручная запись с явным выбором существующего Telegram-аккаунта клиентки. Статусы «Пришла» / «Не пришла» мастер меняет в любое время независимо от времени визита; клиентам изменение статусов недоступно.
- Редактор шаблона дня: выбор часов/минут, ручной ввод, изменение и удаление времени. «Своё время» открывает форму внутри Mini App и сохраняет окошко на выбранную дату.
- Перерывы и отпуск; интервал блокирует всю услугу. Буфер 0–120 минут между визитами.
- Услуги, портфолио, расходы, экспорт записей и расходов в CSV/JSON.
- Журнал изменений, состояние очереди уведомлений и последнего успешного запуска worker.
- Серверная проверка Telegram initData (1 час), доступ мастера по ADMIN_TELEGRAM_ID, закрытые по умолчанию приватные таблицы.
- Цена и длительность фиксируются сервером. Все изменения студии выполняются под SELECT FOR UPDATE. Повтор идентичного запроса возвращает исходную запись; изменение payload с тем же ключом даёт 409.
- При потере ответа браузер проверяет предыдущий запрос перед созданием записи на другое время.

## Запуск

Из корня репозитория: npm ci, затем команды npm run dev / migrate / build / test:ui и npm test. Можно работать непосредственно в этой папке; установка npm ci также поддерживается.

```bash
cp .env.example .env
# Заполни .env; никогда не коммить его.
npm run check:config
npm run migrate
npm run dev
```

Нужен Node.js 22 или 24. Локальный адрес — http://localhost:3000. Настоящее приложение открывается через Telegram с HTTPS URL; браузерного обхода авторизации нет. Контур UI-тестов использует отдельный локальный сервер и фикстуры API; NODE_ENV=test отключает только проверку полноты конфигурации dev-сервера, а не авторизацию API.

## Серверные переменные

| Переменная | Назначение |
|---|---|
| DATABASE_URL | PostgreSQL transaction pooler; при Supabase обычно порт 6543 |
| SUPABASE_URL | HTTPS origin проекта |
| SUPABASE_SERVICE_ROLE_KEY | Серверный ключ Storage |
| BOT_TOKEN | Токен выбранного Telegram-бота |
| ADMIN_TELEGRAM_ID | Числовой ID мастера |
| APP_URL | HTTPS origin production, без пути и завершающего слеша |
| TELEGRAM_WEBHOOK_SECRET | Случайный секрет 32–256 символов из букв, цифр, _ и - |
| CRON_SECRET | Другой случайный секрет того же формата |

Секреты хранятся в серверной среде и Supabase Vault, не в public/. Не отключай проверку TLS. При необходимости установи CA через NODE_EXTRA_CA_CERTS.

## Supabase

1. Создай проект и задай DATABASE_URL, SUPABASE_URL и серверный ключ Storage.
2. Выполни npm run migrate. Команда применяет 001_init.sql и 004_operations.sql, регистрирует контрольные суммы и сохраняет существующие данные. При повторном запуске уже применённые миграции пропускаются. Не изменяй применённые файлы; добавляй следующие версии в список lib/migrations.js.
3. Для нового Storage: npm run migrate -- --storage. Нужны права на storage.buckets. На существующем проекте проверь параметры bucket works перед этим шагом. Он публичен для чтения; загрузка выполняется только авторизованным сервером.
4. Включи pg_cron, pg_net и Vault. Через Dashboard создай nail_app_url и nail_cron_secret (значение CRON_SECRET). Не записывай секреты в SQL-файлы.
5. Для нового планировщика: npm run migrate -- --cron. Если nail-reminders уже создан вручную, сначала проверь существующую задачу и удали только её дубликат при наличии; не создавай второй cron для того же бота.

Для существующей установки сначала прочитай OPERATIONS.md. Новому коду нужны таблицы audit_log и worker_status до переключения production.

Начальный каталог содержит услуги, но не демо-клиентов или вымышленные отзывы. Мастер должен открыть реальные даты. Встроенные фото помечены как примеры.

## Vercel и Telegram

- Root Directory: nail-studio; Framework: Other; Install: npm ci; Build: npm run build; Output: public.
- В Production добавь переменные из .env.example. Для preview используй отдельные тестовые базу/бота либо не подключай серверные секреты вообще. Не направляй боевой cron на preview.
- Публичный health endpoint /api/index?action=health проверяет только живость функции. Защищённая диагностика доступна мастеру из настроек.
- Production webhook/cron должны быть доступны без интерактивного Vercel Authentication.
- npm run bot:setup регистрирует webhook, команды и кнопку меню выбранного бота. Это изменяет настройки бота; не запускай команду для чужого или боевого бота из preview.
- Отправь /start и /id. Установи ID мастера на Vercel. Мастер и клиентка должны разрешить боту отправку сообщений.
- В BotFather укажи production HTTPS URL для Main Mini App.

## Уведомления

Подтверждение записи возвращается сразу после сохранения записи, outbox и аудита в одной транзакции. Для book/change нет ожидания Telegram. Минутный Supabase Cron вызывает защищённый worker; при исправном планировщике подтверждения обычно приходят в течение минуты. Напоминания — за 24 и 2 часа, если этот момент ещё не прошёл. Просроченные более чем на 30 минут напоминания не отправляются.

Изменение визита и отправка его уведомления берут одну advisory-блокировку PostgreSQL. Если отмена уже зафиксирована, worker не отправит старую revision. Если отправка уже идёт, отмена ждёт завершения этой попытки (таймаут Telegram 10 секунд). Другие визиты не берут эту блокировку. Задержанная доставка Telegram после принятия сообщения и дубликаты при сбое после отправки всё ещё возможны: общей транзакции с Telegram нет.

Временные ошибки повторяются до 10 попыток; 400/403 прекращают повторы. Доставленные и остановленные задачи очищаются через 30 дней, идентификаторы webhook — через 7 дней. Финансовая история и журнал изменений автоматически не удаляются.

Ручная запись без выбранного проверенного Telegram-аккаунта видна только мастеру, и сообщения клиентке не отправляются. Контакт сам по себе не доказывает принадлежность аккаунта. При выборе существующей клиентки сервер проверяет ссылку на её прошлую запись, а не доверяет произвольному tgId браузера.

## Данные и ограничения

Студия хранится JSONB-документом. Это сохраняет совместимость с существующей базой. Для нескольких мастеров нужны нормализованные сущности и studio_id. Клиент получает только собственные визиты, доступность на 180 дней и занятые интервалы без чужих контактов/причин перерывов. Кабинет мастера пока загружает всю историю; при росте базы потребуется серверная пагинация админки.

Экспорт содержит персональные данные; доступен только мастеру. CSV защищает текстовые поля от исполнения формул. Экспорт записей/расходов не является полной резервной копией БД.

Удаление фото из галереи пока убирает ссылку, но оставляет объект Storage. Неиспользуемые файлы следует удалять отдельно после проверки ссылок и резервной копии. Для удаления персональных данных из рабочей базы нужен контролируемый процесс, учитывающий аудит и backups; автоматической кнопки массового удаления здесь нет.

Нет предоплаты, листа ожидания и нескольких мастеров. Эти изменения не входят в текущий выпуск.

Структура: public/ — интерфейс, api/ — HTTP, lib/ — правила и хранилище, sql/ — миграции, scripts/ — команды, test/ — проверки. Стили, инструменты мастера, доступность и CSV вынесены из основного клиента в отдельные файлы.
