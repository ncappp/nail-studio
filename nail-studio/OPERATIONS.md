# Выпуск и эксплуатация

## Перед переключением production

1. Создай проверенную резервную копию базы и Storage. Убедись, что можешь восстановить её на отдельном тестовом контуре. Наличие платного PITR зависит от настроек проекта; код не включает его автоматически.
2. Прогони CI: Tests and build. Он включает unit/PGlite, настоящий PostgreSQL с несколькими соединениями и Chromium с фикстурами API.
3. Подключи отдельные тестовые Supabase/бота к preview и выполни npm run check:config, затем npm run migrate. Пройди запись с двух Telegram-аккаунтов, фото, отмену, перенос и реальную доставку.
4. В production выполни только базовую npm run migrate до переключения кода. Новые таблицы добавляются без изменения существующего документа студии. Старое приложение совместимо с ними, поэтому возможен откат к предыдущему деплою. Если Storage/cron уже работают, не переустанавливай их без необходимости.
5. Сохрани Root Directory nail-studio. Переключай deployment после успешной миграции. Проверь health и защищённую диагностику мастера.
6. Проверь последнюю успешную задачу cron, реальные подтверждения/напоминания и журнал ошибок Vercel. HTTP 200 от cron подтверждает обработку вызова, а не доставку каждого Telegram-сообщения.

## GitHub

После первого успешного CI в Settings → Rules → Rulesets создай правило для main: required pull request, обязательная проверка Tests and build, блокировка force push и удаления ветки. Само наличие YAML не включает защиту ветки. Для одного разработчика можно не требовать чужого approval. Подключение GitHub в текущей среде не предоставляет инструмента изменения rulesets; этот шаг остаётся в панели владельца.

## Контроль

- Состояние уведомлений в кабинете: последний worker, pending/dead/expired. Отсутствие успешного запуска больше трёх минут подсвечивается предупреждением.
- В Vercel Function Logs ошибки API содержат X-Request-Id без тела запроса или секретов. Этот ID также возвращается клиенту в ошибке.
- Supabase: cron.job_run_details, net._http_response, приватная outbox. Не публикуй payload — он содержит контакты.
- Настрой внешний монитор последнего cron и ошибок API. Кабинет показывает состояние при открытии, но не отправляет автономные алерты.
- Backup: регулярно проверяй восстановление базы и объектов, не только наличие файла. CSV/JSON из интерфейса содержит только визиты и расходы.

## Права

Серверному runtime нужны права на приватные таблицы и серверную загрузку Storage; браузеру — нет. Для миграций нужны права создавать таблицы/индексы. Не выдавай клиентским ролям политики приватных таблиц ради устранения информационного предупреждения RLS Enabled No Policy: отсутствие таких политик здесь намеренное.

## Ограничения проверки

CI использует отдельный локальный PostgreSQL; test:postgres отказывается работать с внешним адресом и базой без суффикса _test, а также не перезаписывает существующую studio. Это не тест боевой базы. Реальные Telegram и Storage проверяются отдельно на тестовом проекте.
